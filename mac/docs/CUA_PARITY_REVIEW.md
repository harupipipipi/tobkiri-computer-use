# 0.1.4 — Cuaの標準機能を保つための修正

2026-09-21、macOS / Cua Driver 0.28.2。

## 修正した退行

| 原因 | 0.1.4の動作 |
| --- | --- |
| タブ/CDP接続を試みると、その窓の通常のAX/画像入力まで禁止していた | 接続の成否にかかわらずCua標準のネイティブ窓操作を使える |
| skillがブラウザには必ずCDPを要求し、接続できないと作業を停止させていた | 現在のページは観測→AX→画像座標。非表示タブ等で必要な場合にCDPを使う |
| rawの読み取りでも全窓のヘルパー観測を破棄していた | 状態一覧は観測を保持し、入力やネイティブキャッシュ更新は影響する窓だけを失効させる |
| native trajectory replayを一律禁止していた | 元のツールを復元。内容が不透明な一括replayは物理入力を含み得るため承認付きで利用可能 |
| Cua内部の通信タイムアウトだけが30秒だった | MCP登録と同じ180秒に統一。入力のタイムアウト後に自動再送はしない |
| Codex登録が補助ツールだけを最初に公開していた | allモードで56標準ツール＋9補助ツールを公開。compactは任意の省略表示として残す |
| desktop対象のmove_cursorまで仮想表示と誤認していた | Cuaの実ポインタ移動は承認必須。window対象の仮想表示は追加確認なし |
| AX取得を200件で打ち切り、後ろのボタンを落としていた | Cua標準の2000件へ戻す。明示的な増減とelements_completeによる欠落確認も可能 |
| 操作後・ラベル指定時・検証時の自動観測が画像縮尺やAX件数を初期値へ戻していた | 直前に指定した画像サイズ・AX件数・メニュー表示設定を維持する |

接続拒否の後、現在のページを新しく観測して通常入力を行うことは許容する。
ユーザーのタブを切り替えたり、アドレス欄を書き換えたりする自動復旧は行わない。
ヘルパーは観測後のウィンドウタイトル変更を検出して再観測を求める。同じタイトルを
持つタブの切り替えまで判定できるわけではないため、hidden tabには正確なCDP対象を使う。

## Cuaの機能と追加機能の境界

Cuaの各ツール定義（名前、description、inputSchema、annotations、capabilities等）は
取得した値をそのまま公開する。`tobkiri_*`は別名の補助APIで、元ツールを置換しない。
型付きタブAPIの接続拒否は、ネイティブAX/画像入力の禁止を意味しない。

許可済みの既存endpointへの接続、画面読み取り、仮想カーソル、通常の背景入力は追加確認不要。
実キーボード/実マウスや前面フォーカスを借りる場合は実ユーザー承認を維持する。
ログイン等の行為に応じた確認はComputerのルールとユーザー指示に従う。

一括trajectoryの内部には任意の操作があり、現在のraw経路ではその各操作を仲介できない。
そのため一括実行時に承認する。内容が既知で背景操作だけの手順はPythonの個別呼び出しで
追加確認なしに実行できる。将来のホスト内replayでは各操作をbrokerへ通す必要がある。

窓の重なりによる別窓への誤入力、曖昧なキーボード配送、サイズ変更後の古い座標は
ヘルパーで止める。これはCuaの全機能を廃止する制約ではなく、対象が保証できない
ヘルパー呼び出しへのエラーである。実際の別窓誤操作をrawで強行して解決しない。

## 検証

- 単体・回帰テスト142件成功。CDP接続拒否後の通常入力、観測の保持、タイトル変更、
  承認なしの物理入力拒否、窓移動、座標変換、通信失敗等を含む。
- `scripts/live_acceptance.py`: 専用2窓で7項目成功。クリック・文字置換・Apply、
  古い観測の拒否、ズーム座標、操作後の縮尺維持、位置変更後の入力、並列操作、カーソル報告位置。
- `scripts/cua_parity_acceptance.py`: 専用2窓で6項目成功。実ドライバの56標準ツールの
  定義が別プロセスMCPの定義と完全一致。直接Cua・Python・MCPのクリックでカウンタが
  それぞれ1増えること、標準/ヘルパーの画像座標操作が一致することを確認。
- `scripts/target_isolation_acceptance.py`: 8項目成功。同一アプリの窓を重ねたとき、誤入力を
  防ぎつつAXPressは指定した窓だけへ配送できることを再検証した。

実機証跡は`artifacts/acceptance.json`、`cua-parity.json`、`target-isolation.json`。
独立したMCPは0.1.4を読み込む。すでに接続しているMCPは再接続が必要な場合がある。

## Vivaldiで分かったこと

現在のVivaldi PIDにはCDP endpointがなく、Cua自身のexisting-profile設定操作は
`browser_route_unavailable`だった。これはVivaldiのリモートデバッグ設定UIの
自動操作が未対応という結果であり、Vivaldi全体の操作不能やOSの権限不足ではない。

同じ窓でネイティブ背景クリックを送信でき、直後の前面アプリと物理ポインタ位置は不変。
ただし結果は`effect=unverifiable`、直後の画像は不変だった。後の画像では曲の選択画面へ
変化していたが、その原因・クリックとの因果・音声再生は証明していない。
`artifacts/browser-native-recovery.json`にこの限界を記録した。

その後「インターステラーを再生」タスクでも新規Python 0.1.4を確認して再試験した。
AXのAuto Playを1回クリックでき、画面のFREE PLAY表示が「-」から「C5」へ変化した。
タブ・アドレス欄・フォーカス・物理入力は変更していないと同タスクから報告があった。
連続した音声再生までは証明していない。そこで得たAX index 202のAuto Playを手掛かりに、
既定の200件制限による欠落も修正した。
最終版の既定値2000件でもAuto Play（index 202）を取得できることを読み取りだけで確認。
記録は`artifacts/browser-ax-default.json`。この観測も`elements_complete=false`だったため、
2000件で任意の大きさのページ全体を取得できるとは保証しない。

参考: [Cuaのブラウザ対象指定と背景配送](https://cua.ai/docs/concepts/browser-targeting-and-background-delivery)。
任意のブラウザ操作が成功する保証や、Lunaの成功率を測定した結果ではない。
