# Codex Computerとの比較と受け入れ記録

検証日: 2026-09-20 / macOS / Cua Driver 0.28.2。
比較対象は、このCodexに公開されている`cua_repl`のネイティブApp APIです。
同じ専用AppKitアプリで、Increment、Name、Applyを操作しました。

## 実際に得られた差

| 観点 | Codex Computerで確認したこと | Tobkiriでの対応 |
| --- | --- | --- |
| 対象 | `getApp()`でアプリに束縛されたオブジェクトが返る | pid/window_idに束縛した`Window`。複数窓では一意なタイトルかIDを要求 |
| 要素 | 短いAX表示と要素番号 | 名前/role検索と短い要素表。古い番号を観測IDで拒否 |
| 結果 | 操作をまとめ、最後の`getAXState()`で変化を取得 | 操作メソッドが最新状態と差分を返す。弱いモデルが再観測を忘れにくい |
| 画像 | `getScreenshot()` / AXとの同時取得 | 生画像、要素番号付き画像、赤い過去クリック跡、変換付きズーム |
| Python | このセッションに公開されたCodex APIはJavaScript | 公開Pythonパッケージとstdio MCPを用意 |
| 並列性 | 今回は単一アプリの操作だけを比較 | 同一アプリの2窓に独立カーソルで並列ジョブを実行し、両方の増分を確認 |
| ドメイン固有の操作 | DOM等も別の対応面がある | Cua標準のtyped browser toolsを保持。ブラウザ独自機能を再実装しない |

Codex: `click(2); setValue(4, "Codex comparison"); click(5); getAXState()`で
Count増分・入力値・Saved表示を確認できました。Tobkiriでも同じ操作をPythonで実施し、
文字列`Tobkiri Python ✓`とSaved表示をAX・画像で確認しました。

Codexの複数操作＋最後のAX読取は約2.6秒。Tobkiriの3操作は約9.8秒でしたが、
各操作後の画像取得と途中の安定した値検証2サンプルを含むため同条件ではありません。
速度の優位性は主張しません。次の最適化候補は、決定済み操作のまとめ実行と、
意味的な操作後の画像を必要な場面だけに絞る設定です。

## ユーザーのフォーカスを奪わない入力

追加検証では1窓の専用AppKitアプリを背景起動し、set_value、type_text、press_key("a")、
Applyを実行しました。実際に`Background value + typeda`となり、最初の3操作は
Cuaがreadbackを伴う`effect=confirmed`を返しました。type_textはAX経路、press_keyは
synthetic_events経路でした。前面アプリを変える処理やユーザー側のblurは呼んでいません。

読み取り専用のFocusProbeを約50ms間隔で動かし、238サンプルで前面PID、AXフォーカス要素の
role/位置/大きさが同一でした。これはサンプリングであり、要素の値やユーザーのキー内容は
収集していません。任意のアプリ・全ての短いフォーカス変化の不在を証明するものではありません。

Codex Computerでも`setValue → typeText → pressKey → Apply`で
`Codex background + typeda`を確認し、833サンプルで前面PIDが同一でした。この比較時は
前面アプリのAX focused elementが取得できず、role/位置の比較は未確認です。

このケースでは両方ともユーザーの前面フォーカスを解除せずに入力できます。背景キー入力は
全アプリで成功するものではなく、複数窓のPID配送やWebレンダラーなどは別途扱います。
その場合の最終手段としてCuaのforeground経路を公開し、毎回の人間承認を追加しました。
ユーザー許可前に実際の前面/物理入力は試験していません。拒否、期限切れ、対象変更、
grantの再利用、raw経路、排他はモックによる単体試験です。

記録: `artifacts/background-focus.json`、`artifacts/codex-background-focus.json`。
`artifacts/foreground-acceptance.json`には、実際の承認確認で停止してキーが未送信である
結果を保存しています。これは前面入力の成功実績ではありません。

## カーソルずれ

`move_cursor(target={kind:"window",...}, x=210, y=268)`で得られた位置は
`{x:210,y:268}`であり、ウィンドウ画像から画面への変換が行われませんでした。
実ウィンドウ原点`(80,378)`、画像倍率2では、期待位置は`(185,512)`です。
この現象はデスクトップ画像でも確認しました。

本実装は、macOS 0.28.2に限り画像座標からscreen pointsへ変換して送信します。
補正後の2カーソルの報告位置は`(185,512)`、`(695,512)`で、期待値と一致しました。
描画フレームが進んでから取得した`artifacts/painted-cursors.png`でも、2つの
カーソルが対応する画面位置付近に描かれることを目視確認しました。
描画のアンチエイリアスやテーマ形状まで含むピクセル単位の自動照合ではありません。

共有デーモンの描画は非同期です。呼び出し直後（frame=0）の画像ではまだカーソルが
描画されていない場合がありました。そのためAPIの`pixels_verified`は常にfalseを返し、
ドライバ位置の一致だけを「描画確認済み」と偽装しません。デーモンは再起動していません。

### ウィンドウ移動への追従（0.1.1）

以前の補正はカーソルを動かした瞬間の画面原点しか使っておらず、その後に窓を移動すると
カーソルが元の画面位置に残りました。0.1.1では窓内の位置を保存し、100ms間隔で窓を
追跡します。入力前にはCuaのキャプチャ情報を更新し、窓の移動だけならモデルに返した
画像座標・要素・ズーム座標・観測IDを維持します。サイズ/画像倍率/要素配置の変化は拒否します。

新しく背景起動した専用テストアプリで、3回の移動後にカーソルのドライバ報告位置が
一致すること、移動前のズーム座標・要素指定で同じボタンだけが押せることを確認しました。
標準Cua経由の座標/要素トークンも確認し、別窓のカウンタは変わりませんでした。
サイズ変更ではカーソルを無効化し、古い座標を拒否、新しい観測と位置指定で復帰しました。
記録は`artifacts/window-tracking.json`（7項目）、結果画像は`window-tracking-result.png`です。

位置の読み戻しまでの計測は1.25〜1.42秒で、通信・ドライバ側の待機も含みます。
100msはポーリング待機時間であり、実際の描画遅延を100ms以内と保証する値ではありません。
今回の移動試験では描画ピクセルの追従までは目視で確認できていません。
ユーザーが動かしている最中の完全な描画同期・原子的な入力配送には、ドライバ内部の
ウィンドウ相対座標対応が必要です。別接続のカーソルや共有デーモンは変更していません。

元ハーネスでは共有キューから待機中のID以外の応答を捨てる可能性があり、
位置検証は送った値の自己照合でした。新しい通信はIDごとのFutureへ応答を配送し、
位置はドライバから読み返します。元のSwift fallbackは、原点とカーソル先端の差も
持っていました。本パッケージはそのfallbackに依存しません。

## 証拠

- `artifacts/acceptance.json`: 6つの実機チェック、対象、セッション、所要時間。
- `artifacts/native-result.png`: 入力とSaved表示、赤いクリック履歴。
- `artifacts/native-elements.png`: 機械取得した中心座標の番号表示。
- `artifacts/native-zoom.png` / `native-zoom-click.png`: 拡大と元画像への座標変換。
- `artifacts/mcp-acceptance.json`: 別プロセスのMCPサーバー経由で入力結果を確認。
- `tests/`: Retina・縮小・負の画面原点・観測の失効・複数窓・応答順序逆転・切断・タイムアウト等。
- `artifacts/target-isolation.json`: 同一アプリの2窓を重ねた状態での8項目。
  座標クリック・スクロール・ドラッグ・曖昧なキー入力を送信前に拒否し、両窓の
  カウンタと入力欄が変化しないことを確認。AXPressでは指定した窓だけが変化しました。

別窓への誤入力対策は、PIDだけでは入力先のウィンドウが決まらない経路を避けるものです。
画像での対象特定と、OSイベント配送先の特定は別の問題です。特に要素指定のscrollも
実体はその位置へのwheel入力なので、座標クリックと同じ重なり判定を行います。
この対策で検証したケースと、任意のアプリ/OSでの完全な入力隔離は区別します。

実機証拠はローカルの`artifacts/`に置き、通常のソース配布には含めません。
別ディスプレイの負の原点は単体テストで検証し、複数ディスプレイの実機再配置は未実施です。
Windows/Linux、ブラウザ全般、Lunaのタスク成功率は測定していません。

## 弱いモデルへの効果を測る次の評価

同じ専用アプリに対して、標準Cuaとcompactモードの両方で同じモデル・同じタスクを
複数回試し、最終状態の達成、誤クリック数、ツール引数エラー、呼び出し回数、時間を
比較できます。重複したボタン名、窓の移動、2窓、画像縮小を別ケースにします。
現状は決定的なPythonスクリプトの受け入れ結果であり、モデル比較結果ではありません。
