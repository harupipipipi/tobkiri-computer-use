# 0.1.5 — カーソル速度とPythonタイミング制御

2026-09-21、macOS / Cua Driver 0.28.2。

## 原因と修正

Cuaの同じバージョンのOSS実装を確認した。`glide_duration_ms=0`は瞬間移動ではなく、
速度基準の移動を選ぶ指定だった。移動経路の曲率、距離、到着方向によって待ち時間が増える。
`set_agent_cursor_motion`には正の小さい移動時間を設定できるため、本体の改造・再起動や
権限変更をせず、セッション単位の公開設定で高速化できた。

Tobkiriのヘルパー用カーソルは既定で以下を使う。

```python
glide_duration_ms=1
dwell_after_click_ms=0
spring=1
arc_size=0
arc_flow=0
turn_radius=1
```

`Window.set_cursor_speed("normal")`でCua標準の動きへ戻せる。
`Computer(cursor_profile=None)`は初期の速度設定を送らない。共有Cua設定、別タスクの
カーソル、物理ポインタを変更しない。raw Cuaツールは標準の設定を維持するため、
必要なら同じ公開ツールでその名前付きsessionへ速度を指定する。

設定は描画スレッドへ非同期に届く。直後の読み戻しが古い値でも設定失敗とは限らない。
初回の表示はenableを先に送り、1描画フレーム程度待ってから移動する。通常の移動ごとに
その待ちは追加しない。

明示的なAXクリックはCua自身がカーソルを移動するため、ヘルパー側の二重移動を省いた。
ただしCua 0.28.2には、ピクセル入力をAX hit-testで処理するとカーソル移動前に返る経路がある。
そこでは高速な事前移動を1回残し、実際の入力先と仮想カーソルの対応を保つ。

## 操作列

通常の`click()`は毎回スクリーンショット・AXツリーを返す。固定された鍵盤などには
`Window.timeline()` / `tobkiri_timeline`を追加し、最初の観測で座標を確定してから
Pythonの`time.monotonic()`でクリックの時刻を管理し、最後に再観測する。

同じ窓に複数の仮想カーソルを用意し、各`ClickStep`で選べる。入力は窓ごとに直列化する。
異なる窓の操作列は`Computer.parallel()`と共通の`start_at`で並行実行できる。
Cua自身も同一アプリ/PIDの背景操作を直列化するため、物理的な同時押しは保証しない。

窓の存在・タイトル・表示状態・サイズ・兄弟窓の重なりを毎回確認する。窓が移動したら
画像→画面の変換を更新し、入力座標は維持する。サイズ変更、タイトル変更、重なり、
ネイティブ拒否、通信エラー、指定した遅刻許容量の超過では以降の入力を止める。
`stop_event`でPython側から中断できる。遅れをまとめて連打で取り返す処理はしない。
指定テンポを守る`on_late="stop"`が既定。通し演奏を優先する場合は明示的に
`on_late="stretch"`を選び、以降の時刻をずらして続行できる。遅れの累積は
`schedule_shift_seconds`に記録し、元のテンポを守れたと偽装しない。

操作列には前面/desktop入力を提供しない。通常のCua背景配送とフォーカス保護はそのまま。
入力間のページ内容を画像照合しないため、静的なUI向けの明示的なモードである。
スクロール・ページ遷移・レイアウト変更を含む場合は操作列を分けて観測し直す。
内部の`_skip_window_change_detection`など非公開引数は使用していない。

## 実機確認

`scripts/latency_acceptance.py`は専用のTobkiriFixtureだけを操作する。

- 移動のみの比較: 500ms指定時は約0.53〜0.55秒、1ms指定時は約0.03〜0.05秒。
  1msは描画設定であり、RPC込みの実時間が1msになる意味ではない。
- 近接した2点を交互にクリックする比較: 通常設定の中央値約1.55秒から高速設定約0.36秒へ。
  両方ともクリックごとの画面取得を含む。任意のブラウザでも同じ時間になる保証ではない。
- 操作列: 2カーソルを交互に使い、0.25秒間隔（毎秒4回）で12クリック成功。
  送信開始の最大遅れは約45ms。カウンタが12増え、最後の両カーソル報告位置も入力先と一致。
- 2窓の操作列を同じPython開始時刻で実行し、それぞれ4クリック成功。

クリックの送信開始/終了を記録している。OSイベントが実際に届いた時刻、音の立ち上がり、
描画ピクセルの完全な同期は計測していない。各ステップは通常のクリックであり、押下を
保持した鍵盤やサンプル精度の和音演奏のAPIではない。

158件の単体・回帰テストとskill検証も成功。実測詳細は
`artifacts/latency-acceptance.json`、検証画像は`artifacts/latency-result.png`。

実ブラウザの演奏タスクからは、高速設定で32音を完了したとの報告があった。
その後の0.25秒間隔の厳密な操作列では、最初の1クリック完了まで約0.47秒かかり、
次の入力が許容遅れを超えて停止した。ページによってはAX/入力配送の待ち時間が残る。
また、別の同一アプリ試験と競合したMCP試験も2入力後に遅刻停止した。
競合を外したMCP試験では、2カーソル・0.35秒間隔で3入力を完了し、カウンタの増加も確認した。
演奏タスクの追加報告では、`on_late="stretch"`で左右2カーソルを交互に使った8音を
完了した。最後の入力終了は開始から約4.67秒、予定時刻の累積ずれは約2.62秒。
最終観測の鍵盤状態はA3だった。ネイティブ結果はbackground/accessibilityの
`effect=unverifiable`であり、音声や正確なテンポを検証した結果ではない。
毎秒4入力や1msの実時間をすべてのアプリ・負荷条件で保証するものではない。
