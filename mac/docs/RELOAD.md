# 0.1.6 — 接続を維持したMCP更新

Codexが保持する標準入出力の接続をランチャーが維持し、実際のツール処理を子プロセスへ
渡す。更新時は新しい子プロセスの起動とツール一覧を確認してから、古い子プロセスの
所有セッションを終了する。Cuaの共有デーモン、許可設定、別のPythonプロセスは変更しない。

## 更新手順

インストール・検証を済ませてから、そのPython環境で
`tobkiri-computer-use-reload`を実行する。構文を検証してソースのハッシュを記録し、
更新マーカーをatomic renameで公開する。編集中のソースは自動で読み込まない。
マーカー公開後にコードが変わった場合は、更新を完了してもう一度公開する。
新しい処理プロセスは既存のPythonバイトコードキャッシュを使わず、短時間の同じサイズの
修正でも古いコードを再利用しない。

各MCP接続は次のリクエストの境界でマーカーを確認する。実行中の操作とは同じロックで
排他し、演奏・入力の途中で処理プロセスを終了しない。クライアント側が先にタイムアウト
しても、ランチャーは処理を待ち、同じ入力を再送しない。内部の通信までタイムアウト・切断
した場合は結果不明として自動更新・次の入力を止める。対象を別途観測してから再接続する。

`tobkiri_runtime(action="status")`は実際に読み込んだバージョン、generation、
ランチャー/処理プロセスのPIDを返す。`action="reload"`はその接続だけを再読み込みする。
起動引数、driver socket、承認方式をツールの引数から変更することはできない。

更新後は旧観測、AXトークン、ズーム、ブラウザ結び付け、カーソルセッションを破棄する。
更新を検出したリクエストが古い状態を使う操作なら、入力せず`runtime_reloaded`を返す。
新しい観測で続ける。新プロセスの起動失敗や未完成の更新では旧プロセスを保持し、
失敗した更新と同時に来た操作は送らない。

ツール/リソース一覧の変更通知を送信する。ホストがツール定義をキャッシュする場合にも、
既存の`tobkiri_tools(name=...)`で新しいヘルパー定義を取得し、
`tobkiri_call(name=..., arguments=...)`で呼べる。元の56個のCuaツール定義・結果は維持する。
MCPランチャーは11ヘルパー、全体で67ツール。ホスト内で直接使うToolServiceは従来の10ヘルパー。

## 初回移行の境界

0.1.5以前の起動済みサーバーにはこの機能がないため、初回のみMCP接続を更新する。
Codex全体の終了は不要。設定は専用の再読み込みランチャーへ変更済みだが、すでに実行中の
ターンは古い接続を保持することがある。`tobkiri_tools`の`runtime_version`と`runtime`を
確認する。0.1.6の`restartless_reload=true`が得られてから上記の更新経路を使える。
設定変更だけでは既存の接続は切り替わらない。2026-09-21のユーザーによる再起動後、
現在のCodex接続が0.1.6であることを確認済み。その接続上でも`action="reload"`が成功し、
ランチャーPID10796を保持したまま処理PID10848→18700、generation1→2となった。
将来ランチャー自身やPython実行環境・起動引数を更新する際にも、MCPだけの再接続は
必要になり得る。通常のツール処理・skillの更新は処理プロセスの再読み込みで反映する。

Codex自身にも[公式のMCP再読み込みAPI](https://learn.chatgpt.com/docs/app-server)がある
（`config/mcpServer/reload`）。この環境のアプリはstdio接続で起動され、CLIのdaemon proxy用
制御socketはないため、そのAPIを外部から呼ぶ経路としては利用しなかった。
CodexのUIはComputer Useの対象外なので、UI操作による再接続も行っていない。

## 検証

- 同じMCP標準入出力接続でgenerationが1から2へ変化し、ランチャーPIDは同じ、処理PIDは変更。
- 更新前後とも67ツールを列挙。新規MCPと既存の汎用call経由のruntime呼び出しを確認。
- 自動更新時の古い入力拒否、入力中の更新待機、更新失敗時の旧プロセス維持、通信不明時の
  非再送、構文検証、起動引数の保持をテスト。

実機接続の記録は`artifacts/reload-acceptance.json`。UIへの入力は不要な検証。

同じ接続で後にCuaの既定セッションが終了済みとなり、`list_windows`を拒否する事象も発生。
原因は未確定。明示的なruntime reloadでgeneration3/処理PID28249へ交換し、
新しい`list_windows`が成功した。Codex・共有Cuaデーモンの再起動も、入力の再送もしていない。
